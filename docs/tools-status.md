## Scope

Step 2 of the deployment plan: the tools, as one MCP edge function, tested directly (curl and Claude Code). Connecting a host, sign-in, per-user access rules and real in-host views belong to step 3.

Data structure the tools work on: [data-structure-status.md](data-structure-status.md).

## The server — `planned`

- One Supabase edge function named `mcp`, at `https://etofljbxzllkucmearwl.supabase.co/functions/v1/mcp`.
- Speaks MCP over Streamable HTTP, stateless, built with the official MCP TypeScript SDK as in Supabase's guide.
- Reads and writes the database with the backend (service role) key, which stays inside the function.

## Temporary access for this phase — `planned`

The function has a public URL and full access to the data, so it cannot be left open, even with dummy data.

- **Development key**: every request must carry a secret key in a header. The key is stored as a Supabase secret and in a git-ignored local file; never in the repo. Requests without it get 401.
- **Acting user**: rows created by the tools get `owner_id` of the test user `claude@test.com` (decided 2026-10-13). All tools see all rows.
- Both are replaced in step 3 by real sign-in and per-user rules.

## Tools

Common rules:
- Arguments are validated; a bad argument returns an error that names the field.
- `id`, `owner_id`, `created_at` and `updated_at` are never returned.
- Errors come back as MCP tool errors with a plain message.

### list — `planned`
- **Argument**: `entity` — one of `skills`, `todos`, `leads`, `sheets`, `docs`, `slides`.
- **Returns**: every row of that entity, ordered by label number, with all columns except `context`.
- No filters or paging in this phase.

### get — `planned`
- **Argument**: `labels` — one or more labels; entities can be mixed (`["todo:1", "lead:2"]`).
- **Returns**: one record per label with all columns including `context`. A label that does not exist is reported in the result as not found; the other records are still returned.

### write_todo, write_lead, write_sheet, write_doc, write_slide, write_skill — `planned`
Create one record. The label is generated by the database.

| Tool | Arguments |
|---|---|
| `write_todo` | `name` (required), `category`, `due` (date), `importance` (1–3), `status` (true = done) |
| `write_lead` | `name` (required), `full_name`, `email`, `url_linkedin` |
| `write_sheet` | `name` (required), `url` |
| `write_doc` | `name` (required), `url` |
| `write_slide` | `name` (required), `url`, `storage_url` |
| `write_skill` | `description` (required), `guideline` |

- **Returns**: confirmation with the new label and the stored record, or an error.

### note — `planned`
- **Arguments**: `label`, `text`.
- Appends a dated line to the record's context.
- **Returns**: confirmation, or an error (label not found; skills have no context).

## Render instructions — `planned`

Every tool result has two parts:
- `data` — the records or the confirmation.
- `render` — a short plain-text instruction to the host on how to show the result in chat.

In this phase `render` is a placeholder in words. Step 3 decides the real mechanism and replaces it.

| Tool | Render instruction |
|---|---|
| `list` | Table, one row per record. Columns per entity (todos: label, name, category, due, importance, done). Overdue open todos highlighted. |
| `get` | One card per record: label and name as title, fields below, context as a dated list. Urls as links. |
| `write_*` | One-line confirmation with the new label, then the record as a card. |
| `note` | One-line confirmation naming the label. |

## Not in this deployment (decided 2026-10-13)

1. **Updating a record** — not for now. The `write_*` tools only create. Known consequence: a todo cannot be marked done, a due date cannot be changed and a lead cannot be corrected through the tools. Idea on file for later: `write_*` accepts an optional `label`; when given, it updates only the fields supplied.
2. **Deleting a record** — not included. Idea on file for later: a soft delete (archive) by label.


## Testing

- curl scripts for each tool, including the error cases (missing key, unknown entity, unknown label, bad importance, note on a skill).
- The server added to Claude Code as an MCP server, to check the tools read naturally to a model.
- Rows created during testing are removed afterwards; label numbers used by tests are not reused.

## Build order

1. Edge function skeleton with the development key check; deploy; confirm 401 without key.
2. `list` and `get`.
3. `write_*` and `note`.
4. Render instructions.
5. Tests; update the statuses in this document.
